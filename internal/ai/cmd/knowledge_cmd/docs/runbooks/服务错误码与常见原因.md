# 服务错误码与常见原因

## 适用范围

适用于根据接口返回错误码快速判断初步排查方向的场景。错误码只能帮助分类，最终原因仍需要结合请求参数、日志和上下游结果确认。

## 常见现象

- 接口返回固定业务错误码，但调用方不清楚应该检查请求、数据库还是下游服务。
- 同一个批量任务中出现多个错误码，需要先按原因分类再分别处理。
- 错误码含义与现场判断不一致，需要结合日志确认实际失败环节。

## 初步判断

先按错误码确定排查方向，不把错误码直接当成最终根因。参数类问题优先核对原始请求，数据库和下游类问题优先核对对应调用日志，实例不存在则先确认实例 ID 的来源和当前状态。

## 错误码对照

| 错误码 | 初步含义 | 优先排查方向 |
| --- | --- | --- |
| `12000000001` | 调用接口参数错误，例如类型不匹配 | 核对请求字段类型和值 |
| `12000000002` | 数据库更新失败 | 排查数据库更新相关日志 |
| `12000000003` | 下游接口错误 | 核对下游请求和返回错误 |
| `12000000004` | 实例不存在 | 核对上游传入的实例 ID |

## 排查步骤

### 第一步：保留原始请求信息

记录错误码、请求时间、接口名称和相关实例 ID。不要只根据错误码直接修改数据。

### 第二步：核对错误码对应方向

- 如果是 `12000000001`，检查是否把数字传成字符串、字段缺失或类型不匹配。
- 如果是 `12000000002`，检查数据库更新是否失败，并查询相关日志。
- 如果是 `12000000003`，检查下游接口返回和调用链错误。
- 如果是 `12000000004`，检查上游传入的实例 ID 是否错误或已经不存在。

### 第三步：结合日志确认

错误码只提供初步分类。需要结合接口日志、请求参数和下游返回内容确认根因，再决定是否重试、修正请求或升级处理。

## 验证恢复

- 修正问题后，使用同类请求确认接口不再返回原错误码。
- 对数据库或下游调用失败，确认对应依赖恢复，并检查本次请求的最终处理结果。
- 对实例不存在，确认调用方使用的实例 ID 与系统当前记录一致。
- 回查同一时间范围内的同类错误，确认错误数量没有继续增长。

## 常见误判

- 把错误码当成最终根因，不再查看日志。
- 把 `12000000002` 当成下游接口问题，忽略数据库更新链路。
- 看到 `12000000004` 就删除或重建资源，没有先核对上游实例 ID。

## 升级条件

如果错误码含义与日志现象不一致，应保留完整错误上下文和脱敏后的请求摘要，再升级给接口或对应依赖负责人。负责人和升级时限需要由业务团队补充。
